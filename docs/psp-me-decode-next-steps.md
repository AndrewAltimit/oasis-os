# PSP ME H.264 Decode: Next Steps Plan

## Date: 2026-03-24

## Current Status

- **NAL feeding works**: `sceMpegGetAvcNalAu` returns 0 for every frame
- **ME is booted**: `sceMeBootStart660` returns 0
- **Syscall hooks work**: all 5 sceMpeg functions redirected to VSH library
- **AvcDecode fails**: returns `0x80628002` (AVC_DECODE_FATAL) on every frame, pic_num=0
- **PMPlayer works**: proves the hardware CAN decode H.264 on this exact PSP

## Root Cause Hypothesis

The error `0x80628002` comes from kernel `sceAvcodec_wrapper`'s error table at
offset +0x49AC (index [3]). Both the standard `sceMpeg_library` and `sceMpegVsh_library`
call into the same kernel avcodec — the failure is in the kernel code itself.

The empty stub at +0x2388 has **zero callers** — it is not on any code path. The error
is generated by a logic check inside the kernel avcodec's decode pipeline.

PMPlayer works because of something in its initialization or module loading sequence
that we haven't replicated. Possible causes:

1. **Module loading mechanism**: PMPlayer uses `kuKernelLoadModule` + `sceKernelStartModule`
   to load `mpeg_vsh.prx` from flash0. On our EBOOT, `sceKernelStartModule` returns
   `LIBRARY_NOT_YET_LINKED` (0x800200D3). PMPlayer's PRX-mode EBOOT (`BUILD_PRX=1`)
   might get different import resolution behavior.

2. **Kernel avcodec internal state**: The kernel avcodec may check some global state
   or hardware register that's only set during certain initialization sequences.

3. **sceMpegCreate context**: The mpeg context created by our `sceMpeg_library` might
   differ from the one created by `sceMpegVsh_library` in ways that affect the kernel
   avcodec's decode path (even though we hook Create to go through VSH).

## Plan

### Phase A: PMPlayer Runtime Analysis

**Goal**: Capture PMPlayer's exact module loading and function call sequence on our PSP.

1. **Dump PMPlayer's loaded modules at decode time**
   - Our kernel PRX runs alongside all homebrew (it hooks sceDisplaySetFrameBuf)
   - Add a "Dump User Modules" button to the overlay
   - Launch PMPlayer, start playing a video, trigger the dump
   - Compare the module list with what our EBOOT has loaded
   - Key question: which modules are loaded that we don't have?

2. **Hook PMPlayer's sceMpegAvcDecode**
   - Our PRX can hook the syscall BEFORE PMPlayer calls it
   - Log the arguments (mpeg handle, AU pointer, frame_width, init value)
   - Compare with our EBOOT's arguments
   - Key question: are the arguments structurally different?

3. **Hook PMPlayer's sceMpegCreate**
   - Log all 7 parameters PMPlayer passes to Create
   - Compare with ours (especially mpeg_mode, frame_width, ddr_top)

### Phase B: Full Kernel Avcodec Disassembly

**Goal**: Trace the exact code path from sceMpegAvcDecode syscall to the
error table load that produces 0x80628002.

Binary: `/home/mikunpc/Downloads/me_dump/53_sceAvcodec_wrapper.bin` (19,036 bytes)
Base: varies per boot (use relative offsets)

1. **Identify the AvcDecode entry point**
   - Find the syscall handler for NID 0x0E3C2E9D (sceMpegAvcDecode)
   - This is in the export table, not the import stubs
   - The function at the beginning of the module handles syscall dispatch

2. **Trace the decode code path**
   - Use Capstone to disassemble from the entry point
   - Follow all JAL/J/branch targets
   - Build a call graph of the decode pipeline
   - Identify where the error table at +0x49A0 is accessed

3. **Find the 0x80628002 return site**
   - The error table stores 0x80628002 at +0x49AC (index [3])
   - The code accesses it via a base register + offset
   - Find all code that loads from +0x49AC relative to any register
   - Trace backward from each load site to find the condition that triggers it

4. **Compare with working path**
   - The same code works when called from the VSH movie player
   - The condition check must involve some context/state that differs
   - Candidates: mpeg handle internals, EDRAM state, ME boot mode,
     codec buffer version, thread attributes

### Phase C: Build Custom Decode Bridge (if B doesn't resolve)

If the kernel avcodec's logic check is unfixable, build a complete
bypass using the ME RPC protocol we reverse-engineered.

1. **Create a minimal kernel PRX** that:
   - Exports a custom `oasisMeAvcDecode(codec_buf)` function
   - Internally calls `sceMeVideo_driver::Decode` (NID 0x6D68B223)
   - Manages the codec buffer translation from sceMpeg AU to
     sceVideocodec codec_buf format
   - Returns decoded frame pointer

2. **Wire the EBOOT to call through the custom PRX**
   - After `sceMpegGetAvcNalAu` succeeds (AU is in the ES buffer)
   - Instead of calling `sceMpegAvcDecode`, call `oasisMeAvcDecode`
   - This bypasses kernel avcodec entirely

3. **Implement YCbCr → RGB conversion**
   - Either via `sceMpegBaseCscAvc` (if it works without avcodec)
   - Or via VFPU scalar conversion (proven fallback)

### Phase D: Alternative — Use PMPlayer's Prebuilt PRX Directly

The most pragmatic fallback: extract the exact set of PRX files that
PMPlayer loads and ship them with OASIS OS.

1. Copy PMPlayer's `cooleyesBridge.prx` + `mpeg_vsh370.prx` (or flash0 mpeg_vsh)
2. Build our EBOOT as `BUILD_PRX=1` to match PMPlayer's module attributes
3. Link against the same stub libraries PMPlayer uses
4. This requires porting the build to use PSPSDK's PRX toolchain

## Recommended Order

1. **Phase A** first — cheapest to implement, highest information value
2. **Phase B** if A reveals the kernel condition
3. **Phase D** if we need a quick win
4. **Phase C** as the nuclear option (most work but guaranteed to work)
