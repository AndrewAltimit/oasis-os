# Internationalization (i18n)

OASIS_OS ships its UI strings in `crates/oasis-i18n`. Translations are TOML
files compiled into the binary (`crates/oasis-i18n/translations/<code>.toml`);
lookups go through a process-wide current locale.

## Locales

| Code | Language | Rendered by the bitmap font |
|------|----------|-----------------------------|
| `en` | English | yes (reference catalogue) |
| `es` | Español | yes |
| `de` | Deutsch | yes |
| `fr` | Français | yes |
| `ja` | 日本語 | **no**, UI falls back to English |
| `zh` | 简体中文 | **no**, UI falls back to English |
| `ko` | 한국어 | **no**, UI falls back to English |

## Selecting a locale

The user picks a locale in **Settings → Language**. The Settings app posts
the locale code to `/system/ipc/locale`; the host:

1. stores it as `prefs.locale` in `/system/settings.toml` (and, on desktop,
   mirrors that file to real storage so it survives a restart; see
   `crates/oasis-app/src/user_prefs.rs`),
2. calls `oasis_i18n::set_ui_locale(locale)`, which activates the locale,
3. rebuilds locale-dependent chrome (start menu labels, bottom-bar date) and
   publishes the choice at `/system/state/locale`.

At boot the SDL host reads the persisted preference and calls
`set_ui_locale` before any UI is built.

## Font coverage and the English fallback

Desktop, UE5 and PSP draw text with the built-in 8x8 bitmap font
(`oasis_types::bitmap_font`). It covers ASCII, Latin-1, common symbols and
basic Cyrillic. It has no CJK glyphs. Japanese, Chinese and Korean strings
would therefore render as "tofu" boxes.

`oasis_i18n::bitmap_font_supports(locale)` checks every string of a locale
against `bitmap_font::has_glyph`. `set_ui_locale` activates
`ui_locale_for(requested)`: the requested locale when it is fully drawable,
English otherwise. It logs a warning:

```text
oasis-i18n: bitmap font cannot render 'ja' (Japanese); UI falls back to English
```

The user's choice is still persisted and shown in Settings, where the
language list uses English names for undrawable locales (e.g.
`Japanese (ja)`) and a note explains the fallback. Once a CJK-capable font
path exists, extending `bitmap_font_supports` (or the glyph source it
checks) is enough to enable these locales. The PSP backend's system TrueType
fonts are one candidate.

The unit test `test_bitmap_font_coverage` fails if a Latin-script
translation introduces a character outside the font, such as `œ` (U+0153).

## Using translations in code

```rust
use oasis_i18n::tr;

let label = tr!("settings.cat_audio");                 // &'static str
let date = tr!("date.format", month = m, day = d, year = y); // String
let title = oasis_i18n::translate_app_title("File Manager"); // localized app name
```

Current call sites:

- `oasis-core`: start menu labels (`startmenu.rs`), media tab labels and the
  localized date (`bottombar.rs`), and taskbar button titles for built-in
  apps (`taskbar.rs`).
- `oasis-app-settings`: category tabs, section headings, control labels,
  hints and footer.

Strings that act as identifiers stay English: app titles used for launching,
skin names, IPC payloads, and technical System/About readouts.

## Adding or changing keys

1. Add the key to `en.toml`. English is the reference and the fallback for
   any missing key.
2. Add the same key to **every** other locale file. The tests
   `test_all_en_keys_present_in_all_locales`,
   `test_no_locale_has_keys_missing_from_english` and
   `test_translations_keep_placeholders` enforce matching keys and matching
   `{placeholder}` names.
3. For `es`/`de`/`fr`, stay within Latin-1 so the bitmap font can draw the
   string. For example, write `oe` instead of `œ` and use plain quotes.

Sections: `ui`, `menu`, `terminal`, `app`, `system`, `greeting`, `shell`
(start menu / media tabs), `date` (month names + `format`), `settings`
(Settings app).
