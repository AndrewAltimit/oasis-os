The 90-Frame Deadlock: Patching a PSP Firmware Bug at Runtime

After achieving hardware H.264 decode on the PSP Media Engine, we discovered that sceMpegAvcDecode deadlocks after exactly ~90 frames on >480p content. No flush API works. No reset is possible. We traced the blocking call through the loaded PRX, found the exact kernel import that hangs, and built a runtime binary patch — then started building an alternative decode path through the PSMF ringbuffer.

Entry 08 reverse-engineering, media-engine, firmware-patching

The Setup: Video Streaming Works, Then Freezes

Entry 07 ended with working H.264 hardware decode via mpeg_vsh370.prx on our PSP-3001. The TV Guide app streams video from archive.org over TLS 1.3, demuxes MP4 on the fly, and feeds H.264 NAL units to the Media Engine for decode. Audio plays via sceAudiocodec on a separate thread. Everything initializes. Frames decode. Video appears on screen.

Then, after exactly ~90 frames, the video freezes and never recovers.

The content is 656×480 Main profile H.264 (mode 5 in the ME’s terminology). The first ~75 decoded frames are perfect — zero errors, zero corruption. Then sceMpegAvcDecode enters and never returns. The video thread blocks permanently. Audio continues on its own thread, but the I/O thread eventually stalls too (blocked on video queue backpressure), and the stream dies.

Phase 1: Streaming Performance Optimizations

Before investigating the deadlock, we eliminated a massive performance bottleneck in the streaming pipeline. The PSP’s 333 MHz Allegrex CPU and slow heap allocator were being hammered by per-frame allocations:

OptimizationWhat ChangedSavings
Pre-allocated video texture Reuse persistent GU texture buffer across frames ~30 MB/s alloc churn eliminated
Remove StreamFrame copies Send raw AVCC directly, clone SPS/PPS only on keyframes ~3 MB/s alloc churn eliminated
Static RGBA double-buffer decode_into() writes to pre-allocated buffers ~15 MB/s alloc churn eliminated
Semaphore-based wakeup Replace 5ms polling with kernel semaphore CPU waste eliminated
Audio thread re-pop Immediately check queue after output_blocking ~20 wasted wakeups/frame eliminated
Range D-cache flush Replace full D-cache invalidate with range ops in AAC init 16KB D-cache thrash avoided
Conditional vlog Suppress Memory Stick I/O during active decode 5–20ms stall per log eliminated

Total: ~48 MB/s of heap allocation churn eliminated on a 333 MHz MIPS CPU with a basic allocator. These optimizations are valuable regardless of the deadlock — they make the first ~3 seconds of video smooth and responsive.

Phase 2: Hunting the Deadlock

We added a DECODE_STEP atomic watchdog: the decode function sets step=1 before sceMpegGetAvcNalAu, step=2 before sceMpegAvcDecode, step=3 before sceMpegAvcDecodeDetail2, step=4 before sceMpegBaseCscAvc, and step=0 on return. The main thread checks this every 2 seconds.

Result: step=2 every time. The hang is inside sceMpegAvcDecode itself.

We then systematically tested every mitigation we could think of:

ApproachResult
Full D-cache flush before every decodeNo effect
DDR workspace 2 MB → 4 MBNo effect
Decode rate throttling (16ms / 33ms)No effect
SPS max_ref_frames patching (3 → 1)Made it worse (1 frame vs 90)

sceMpegAvcDecodeFlush mid-streamHard crash

Frame skipping (“ME rest”)Deadlocks on resume

The deadlock is not caused by DPB overflow, cache coherency, decode speed, pixel format, or buffer sizes. It’s a hard ~90-frame limit in the ME firmware’s mode 5 code path. Mode 4 (≤480p) works indefinitely but cannot decode >480p content at all.

Phase 3: Reverse Engineering mpeg_vsh370.prx

The deadlock is inside the loaded PRX, not in our code. To understand it, we needed to trace the full call chain from our Rust sceMpegAvcDecode call through the PRX to the blocking point.

Finding the real function address

The psp_extern! macro generates a stub that loads a function pointer and does an indirect call (jalr $t1). We dumped the stub’s instructions at runtime to extract the import stub address, then followed the j <target> instruction to find the PRX function: 

// Runtime dump of the psp_extern! wrapper:
0x08a656b8+24: jal 0x08a657c0      // marshalling function
               jalr $t1            // indirect call to import stub

// Import stub (patched by kernel at module load):
0x08aaeed4: j 0x08d6dbc0          // jump to PRX function

// PRX function prologue:
0x08d6dbc0: addiu $sp, $sp, -0x20  // this is sceMpegAvcDecode

Mapping the PRX structure

We disassembled the 42 KB code segment of mpeg_vsh370.prx using Capstone (MIPS32 little-endian). Matching the loaded function’s prologue bytes against the raw PRX identified it as VA 0x71c0 — one of four identical dispatch wrappers. These check an initialization counter and call the real implementation: 

sceMpegAvcDecode Call Chain (mpeg_vsh370.prx)

VA 0x71c0  dispatch wrapper
    │  checks init state (< 0x3E0 → return error)
    │  saves registers, calls real function
    ▼
VA 0x1078  real sceMpegAvcDecode
    │
    ├── 0x26e4  validate MPEG handle
    ├── 0x616c  AU stream lookup
    ├── 0x8650  ME decode trigger ← BLOCKING FUNCTION
    │     │
    │     ├── 0x8234  WaitSema(mpeg_data+0x66c)  // mutex acquire
    │     ├── 0x9fd4  KERNEL IMPORT STUB ← INFINITE WAIT
    │     └── 0x82c4  SignalSema(mpeg_data+0x66c) // mutex release
    │
    ├── 0x8880  pre-CSC setup
    ├── 0x8a80  ME decode data copy
    └── 0x9f6c  kernel syscall (in loop)
Full call chain traced via Capstone disassembly + runtime instruction dumps.

The blocking point: kernel import stub 0x9fd4

Function 0x8650 is the critical wrapper. It acquires a mutex semaphore at mpeg_data+0x66c, calls the kernel import at VA 0x9fd4, then releases the mutex: 

// VA 0x8650 — ME decode trigger
lw    $a0, 0x240($s0)      // load semaphore ID
jal   0x8234               // WaitSema (acquire mutex)
move  $a0, $s1             // decode context
jal   0x9fd4               // KERNEL CALL — blocks forever
move  $a1, $zero
lw    $a0, 0x240($s0)      // load semaphore ID
jal   0x82c4               // SignalSema (release mutex)
move  $v0, $s1             // return result

The import stub at 0x9fd4 is patched by the kernel at module load time to jump into the kernel’s ME RPC handler. That handler calls WaitEventFlag(SceMediaEngineRpc, 1, WAIT_AND|CLEAR, &out, 0) with timeout=0 (infinite). When the ME coprocessor deadlocks after ~90 frames, it never sets the event flag, and the wait blocks forever.

Why signalling the semaphore doesn’t help

We tried reading the semaphore ID from mpeg_data+0x66c and signalling it from the main thread. No effect — because the semaphore is the mutex, not the completion signal. Function 0x8650 has already acquired the mutex (line 2) and is blocked on the kernel call (line 4). Signalling the mutex just increments its count for the next caller. The current holder is past the mutex, stuck in the kernel.

Phase 4: Runtime Binary Patching

Since we can’t flush, reset, or recreate the decoder — and we can’t unblock the kernel wait — we took a different approach: prevent the deadlock by patching the loaded PRX in memory.

After the decoder initializes, we compute the PRX base address from the resolved import stub (a j <target> instruction that the kernel patched at load time). The jal 0x9fd4 instruction at PRX VA 0x8678 is the call to the blocking kernel function. After 85 frames (safely before the ~90 deadlock threshold), we overwrite it: 

// Before patch (normal ME decode):
0x8678: jal 0x9fd4           // call kernel ME RPC
                              // → WaitEventFlag(infinite) → DEADLOCK

// After patch (skip ME call):
0x8678: addiu $v0, $zero, -1 // return error immediately
                              // → caller sees error, continues

The patch is a single MIPS instruction replacement: 0x2402ffff (addiu $v0, $zero, -1) overwrites the jal instruction. The delay slot (already move $a1, $zero) is harmless. We flush the D-cache after patching to ensure the CPU fetches the new instruction.

Result: ~70 decoded video frames (~2.3 seconds at 30fps), then the patch activates and every subsequent decode returns an error. The video thread handles errors gracefully and continues running. Audio plays uninterrupted for the full stream duration. The system is completely stable — tested with 940+ frames processed, zero crashes.

Phase 5: The Event Flag Dead End

The ideal fix would be to add a timeout to the infinite WaitEventFlag call. We know the event flag is named SceMediaEngineRpc and is created by the sceMeCodecWrapper kernel module. If we could find its UID, we could either hook sceKernelWaitEventFlag to add a timeout, or signal it directly from a watchdog.

We scanned UIDs 1–65,536 with sceKernelReferEventFlagStatus from both user mode and a kernel plugin thread. Zero event flags found in either context. The kernel’s event flag enumeration appears to be restricted to the creating process/partition. We added a delayed kernel thread (scanning every 5 seconds for 60 seconds after boot) to catch the flag after sceMpegInit creates it. Still nothing. Dead end.

Phase 6: The PSMF Ringbuffer Alternative

There are two paths to the ME’s H.264 decoder:

PathModuleAPIData Format
NAL direct (current) mpeg_vsh370.prx sceMpegGetAvcNalAu Raw AVCC NAL units
PSMF ringbuffer AvMpegBase (system) sceMpegGetAvcAu MPEG-PS packs in PSMF container

The ringbuffer path uses AvMpegBase (Sony’s built-in MPEG module) with sceMpegCreate mode 0. This is the standard path used by UMD video playback and every commercial PSP game. It’s a completely different ME firmware code path — and might not have the 90-frame bug.

Byte-level PMF format analysis

Previous attempts to use the ringbuffer path failed because the kernel’s MPEG-PS demuxer rejected our generated data. This time, we hex-dumped a real Sony PMF file (test.pmf on the Memory Stick) and reverse-engineered the exact byte layout: 

PSMF File Layout (from real Sony PMF)

Offset    Size    Content
──────    ────    ───────────────────────────────────
0x0000    2048    PSMF Header ("PSMF0015" + stream descriptors)
0x0800    2048    Pack 0: Pack header(14B) + System header(18B) + Index(254B+)
0x1000    2048    Pack 1: Pack header(14B) + Audio PES 0xBD (2028B)
0x1800    2048    Pack 2: Pack header(14B) + Audio PES 0xBD (2028B)
0x2000    2048    Pack 3: Pack header(14B) + Video PES 0xE0 (179B) + Padding
0x2800    2048    Pack 4: Pack header(14B) + Audio PES 0xBD (2028B)
  ...     ...     Alternating audio/video packs

Key format rules:
  • Every pack = exactly 2048 bytes (matches ringbuffer packet size)
  • Pack header = 14 bytes: 00 00 01 BA + MPEG-2 SCR(6B) + mux_rate(3B) + F8
  • First pack MUST have system header (00 00 01 BB) + index (00 00 01 BF)
  • PES fills remaining pack; short PES followed by padding (00 00 01 BE)
  • H.264 data inside video PES is Annex B format (start codes)
Every detail derived from byte-level comparison with a real Sony PMF file.

Building the MPEG-PS wrapper

We implemented two new modules:

  • psmf.rs — MPEG-PS pack builder. Generates 2048-byte packs with correct MPEG-2 SCR timestamps, PES headers with PTS, and padding streams. Splits large H.264 access units across multiple continuation packs.
  • psmf_decode.rs — Ringbuffer decoder. Creates an sceMpeg instance with mode 0 (standard), constructs a ringbuffer with a callback function, feeds MPEG-PS packs, and calls sceMpegGetAvcAu + sceMpegAvcDecode.

Current status

The PSMF init chain succeeds completely on real hardware: 

[PSMF] AvMpegBase load=0x0              // system module loaded
[PSMF] sceMpegInit=0x0                  // MPEG subsystem ready
[PSMF] memSize=65536                    // mode 0 buffer size
[PSMF] ringbuffer constructed            // 64 packets, callback set
[PSMF] mpeg created                     // mode 0 instance
[PSMF] stream registered                // video stream 0xE0
[PSMF] QueryStreamOffset=0x0 offset=0x800  // header ACCEPTED
[PSMF] put 2 packs, ret=2               // header + system pack fed
[PSMF] header sent OK                   // ready for video data

The PSMF header passes sceMpegQueryStreamOffset validation, and the first two packs (header + system header) feed successfully via the ringbuffer callback. The kernel’s MPEG-PS demuxer currently crashes when processing our video packs — the format is close but not yet byte-perfect. This is the active investigation frontier.

What We Learned

  • The ME firmware has a hard ~90-frame limit in mode 5. It’s not DPB size (proven by SPS patching making it worse), not cache coherency (proven by full D-cache flush), not buffer sizes (proven by DDR workspace doubling), and not decode speed (proven by throttling). The limit is in the ME coprocessor’s internal state.
  • Every sceMpeg flush/reset API crashes on mpeg_vsh370.prx. sceMpegFlushAllStream, sceMpegAvcDecodeFlush, and sceMpegInit all cause hard freezes when called during active decoding. The decoder cannot be safely reset without destroying it, and destruction crashes too (ME is busy).
  • Runtime binary patching of loaded PRX modules works. Computing the PRX base from the resolved import stub address, locating a specific instruction by VA offset, and overwriting it with a D-cache flush — all from user-mode Rust — is a viable technique on PSP.
  • mpeg_vsh370.prx and AvMpegBase are mutually exclusive. Both register the sceMpeg library. mpeg_vsh370 supports modes 4/5 (NAL path). AvMpegBase supports mode 0 (ringbuffer path). Loading AvMpegBase before mpeg_vsh370 allows the PSMF path to initialize correctly.
  • Kernel event flags are not enumerable from plugin threads. sceKernelReferEventFlagStatus returns errors for all UIDs from both user mode and kernel plugin threads, even after the event flag is created.
  • The PSMF format is strict but discoverable. Byte-level analysis of a real Sony PMF file reveals the exact pack structure, PES formatting, and alignment requirements. The kernel’s sceMpegQueryStreamOffset validates the PSMF header, providing a concrete pass/fail signal for format correctness.

What’s Next

  • Fix the PSMF video pack format: The kernel’s MPEG-PS demuxer crashes on our video packs. Isolating which byte pattern triggers the crash (pack-by-pack feeding is implemented) will narrow down the format difference from the real PMF.
  • Test ringbuffer path for >480p: If the PSMF path works, test whether AvMpegBase mode 0 can sustain unlimited H.264 decode at 656×480 — the original content that triggers the mode 5 deadlock.
  • Decode the ME firmware: Decrypt me_t2img.img to understand what internal state accumulates after ~90 frames in mode 5 — the one approach that could fix the root cause.
