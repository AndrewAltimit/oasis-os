PSP USB Host Mode: Reverse Engineering Sony's Hardware for Peripheral I/O

An active hardware research project to enable the PSP's USB controller as a host — supplying VBUS power, enumerating devices, and communicating with microcontrollers via USB serial. Firmware reverse engineering meets Rust kernel modules.

Entry 05 hardware, reverse-engineering, in progress

The Premise

The PSP's Tachyon SoC contains a USB controller capable of both device and host operation at the silicon level. Under normal operation — stock firmware or custom firmware — the USB port works exclusively in device mode: the PSP presents itself as a mass storage device to a connected PC.

But Sony's first-party accessories prove that host mode works. The Go!Cam camera (PSP-300), 1seg TV tuner (PSP-S310), GPS receiver (PSP-290), and microphone all connect via the Mini-B port with the PSP acting as host. Sony's kernel modules in flash0:/kd/ handle the mode switch, but they're undocumented and restricted to specific vendor/device ID pairs.

No one has ever shipped public USB host mode homebrew for the PSP. The rust-psp SDK, with its kernel mode support and 829 syscall bindings, is uniquely positioned to be the first.

Key Hardware Facts

  • The USB controller supports USB 2.0 Full-Speed in both device and host mode
  • VBUS power switching is firmware-controlled, not OTG ID pin detection
  • The Mini-B connector is not Mini-AB (no OTG), confirming that host mode is activated entirely through register writes
  • Memory-mapped registers at 0xBE2xxxxx (uncached kernel address space)
  • Sony's accessories draw 150–300mA — the VBUS circuit must support at least this range
  • Standard USB cables work — no special OTG wiring, ID pin grounding, or modified cables needed

The Research Plan

Phase 0: Tooling & Power Measurement
VBUS Current Capacity Testing
Using an FNIRSI FNB58 inline power meter and DROK LD25 adjustable load to determine the PSP's actual VBUS current ceiling. Incrementally increase current from 0.25A while monitoring voltage — record the point where VBUS drops below 4.75V. Test both PSP-1000 and PSP-3000 to document per-Tachyon-revision limits. Current working estimate: 300mA.
Phase 1: Firmware Reverse Engineering
USB Module Disassembly & Register Mapping
Decrypt and disassemble usb.prx, usbhost.prx, usbacc.prx, and usb_cam.prx from 6.20 firmware using PSARDumper + pspdecrypt + Ghidra with the PSP processor module. Trace LUI/ORI sequences to identify USB controller register addresses. Map the mode switch mechanism and VBUS power control path. Resolve all sceUsb* NIDs for 6.20.
Phase 2: Host Controller Driver
MMIO Abstraction & Mode Switching
Implement the hardware abstraction layer in Rust: volatile MMIO register access, VBUS power enable/disable with safety guards, host controller initialization, SOF generation, and port status monitoring. All register access occurs in kernel mode via a dedicated PRX module.
Phase 3: USB Enumeration
Device Discovery & Standard Requests
Endpoint Descriptor and Transfer Descriptor management in DMA-accessible uncached memory. Control transfer engine for SETUP/DATA/STATUS phases. Device enumeration state machine: SET_ADDRESS, GET_DESCRIPTOR, SET_CONFIGURATION. Memory allocated via sceKernelAllocPartitionMemory with 4KB alignment.
Phase 4: CDC/ACM Serial Driver
USB Serial Communication
Bulk IN/OUT transfer scheduling for serial data. CDC/ACM class requests (SET_LINE_CODING, SET_CONTROL_LINE_STATE). Target peripheral: Luckfox Pico Pro/Ultra RV1106 running USB-CDC gadget mode. First proof of concept: PSP sends serial data to a Linux SBC.

The Proposed API

The end goal is a safe Rust API for USB host operations, feature-gated behind usb-host in the psp crate: 

#![no_std]
#![no_main]

psp::module!("usb_serial_demo", 1, 0);

fn psp_main() {
    psp::enable_home_button();

    // Initialize host mode, enable VBUS, wait for device
    let mut serial = psp::usb::class::cdc::UsbSerial::open(115200)
        .expect("Failed to open USB serial");

    serial.write(b"Hello from PSP!\n").unwrap();

    let mut buf = [0u8; 64];
    loop {
        if let Ok(n) = serial.read(&mut buf) {
            serial.write(&buf[..n]).unwrap(); // echo
        }
    }
}

Behind this simple API lies a four-layer architecture: hardware abstraction (MMIO registers), host controller driver (transfer scheduling), USB class driver (CDC/ACM protocol), and the user-facing safe API that bridges kernel PRX to user-mode code.

Risk: The Unknown Register Map

The highest-risk element is Phase 1: the USB controller's register layout is undocumented. The approach is multi-pronged:

  • Static analysis: Disassemble Sony's USB modules, trace LUI/ORI instruction pairs that construct 0xBE2xxxxx addresses
  • Cross-reference: Compare against known USB controller IP blocks (Synopsys DesignWare is a common embedded USB IP core)
  • Differential probing: Dump register state before and after Sony's USB driver loads, compare to identify which registers change
  • Community resources: uOFW project firmware RE, PSP-RE Ghidra scripts, ps2dev forum archives from 2006–2012

If the controller uses a recognizable IP block, the register map could be substantially complete in weeks. If it's fully proprietary Sony silicon, this phase extends significantly. Either way, the documentation will be published for the PSP reverse engineering community.

Why This Matters

USB host mode on the PSP enables entirely new categories of homebrew:

  • USB serial → microcontrollers: Talk to Arduino, ESP32, RP2040 over USB CDC/ACM. The PSP becomes a portable debugger or control interface.
  • USB HID → keyboards and gamepads: Standard USB input devices connected to a handheld from 2004.
  • USB mass storage → flash drives: Read and write USB flash drives, removing the Memory Stick dependency.
  • Luckfox Pico integration: A Linux SBC drawing ~250mA connected directly to the PSP's USB port — enabling camera, AI inference, or network bridge capabilities through a 4cm adapter stack.

For OASIS_OS specifically, USB host mode means the PSP backend gains peripheral I/O capabilities that were previously impossible. The terminal could communicate with hardware, the file manager could browse USB drives, and plugins could interface with external sensors. All through the same trait-based backend architecture described in Entry 01.
