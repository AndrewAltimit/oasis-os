Reverse Engineering the PSP Media Engine: From Empty Stubs to Hardware Video Decode

On ARK-4 CFW, H.264 video decode from PSP homebrew fails with a cryptic error — the official sceVideocodec API returns 0x806201FE and nobody has documented why. We traced the problem to empty firmware stubs, discovered hidden kernel modules, reverse engineered the Media Engine’s RPC protocol, found undocumented parameters in PMPlayer’s source code, and achieved hardware-accelerated H.264 video streaming from a Rust EBOOT.

Entry 07 hardware, reverse-engineering, media-engine

The Problem: Error 0x806201FE on ARK-4 CFW

The PSP contains a dedicated coprocessor called the Media Engine (ME) — a second MIPS CPU clocked at up to 333 MHz, designed specifically for multimedia decode. Sony’s games and UMD movies use it for H.264, MPEG-4, AAC, and ATRAC3+ decoding. Early homebrew video players like PMPlayer and PMP Mod successfully used the ME on older CFW configurations, proving it was accessible from homebrew in principle.

On our hardware — a PSP-3001 running ARK-4 CFW on firmware 6.61 — the official sceVideocodec API returns error 0x806201FE on every call. The higher-level sceMpeg API fails too, as it internally delegates to sceVideocodec and hits the same wall. The root cause turned out to be CFW-specific: the kernel modules that bridge user-mode codec calls to the Media Engine are not loaded by sceUtilityLoadModule on this configuration.

We set out to understand exactly why the API fails on ARK-4 and whether there was a way to communicate with the ME directly — bypassing the broken stubs entirely. What we found was a complete, previously undocumented kernel driver architecture and RPC protocol that documents how Sony’s codec firmware communicates with the ME.

Phase 1: Runtime Module Discovery

Our kernel PRX (oasis-plugin-psp) hooks sceDisplaySetFrameBuf to draw an overlay UI on top of running games. We added a “Dump ME FW” menu item that enumerates all loaded kernel modules during UMD Video playback — specifically while playing a Spider-Man 2 UMD movie disc.

The initial dump returned only 32 modules. A subtle API quirk was responsible: sceKernelGetModuleIdList’s second parameter is the buffer size in bytes, not the element count. With a 128-entry buffer of SceUID (4 bytes each), the correct size parameter is 512, not 128. After fixing this, we found 68 modules loaded during UMD video playback.

Buried in the list were two modules that do not appear during normal homebrew execution and are not documented in any public PSP SDK or wiki:

ModuleSizePurpose
sceMeCodecWrapper 11 KB ME firmware loader + RPC bridge between main CPU and ME
sceAvcodec_wrapper 19 KB Kernel-mode avcodec with ME driver imports (replaces the stub version)

This was the first clue. The avcodec.prx loaded during normal homebrew execution contains empty stubs — functions that exist but do nothing. During UMD boot, the firmware loads a different set of modules that include the actual ME driver code. The error 0x806201FE comes from these empty ME submission stubs returning failure.

Phase 2: ME Driver Architecture

With the module names in hand, we used sctrlHENFindFunction (an ARK-4 CFW API that resolves kernel function pointers by library name and NID) to map the imports of sceMeCodecWrapper. It imports from six internal ME driver libraries:

LibraryFunctionsRole
sceMeWrapper_driver 23 Master interface — orchestrates all ME operations
sceMeVideo_driver 7 H.264 and MPEG-4 video decode
sceMeAudio_driver 5 AAC and ATRAC3+ audio decode
sceMeMemory_driver 3 ME-side memory allocation (eDRAM management)
sceMeCore_driver 4 ME lifecycle: boot, halt, reset, RPC dispatch
sceMePower_driver 5 ME clock frequency and power state control

In total, we extracted 47 NIDs for internal ME driver interfaces. These NIDs are not present in any public NID database. The ME firmware itself is loaded from flash0:/kd/resource/me_t2img.img — a 392 KB encrypted image. Other ME firmware files referenced in older documentation (meimg.img, me_blimg.img, me_sdimg.img) do not exist on firmware 6.61.

Inter-processor communication uses two kernel synchronization primitives: a semaphore named SceMeRpc for mutual exclusion and an event flag named SceMediaEngineRpc for completion signaling.

Phase 3: flash0 Extraction

To disassemble the ME driver code, we needed the actual PRX files from flash0:/kd/. This directory is completely inaccessible from user mode — ARK-4 CFW blocks all reads. However, our kernel PRX runs in kernel mode and can read any file on the system.

We extracted all codec-related PRX files and the ME firmware image, writing them to ms0:/ (Memory Stick) for analysis on a desktop machine:

  • me_wrapper.prx — the RPC bridge (sceMeCodecWrapper)
  • avcodec.prx — the stub version loaded during homebrew
  • mpeg.prx, mpeg_vsh.prx — MPEG demuxer layers
  • videocodec_260.prx — version-specific video codec module
  • codec_09g.prx — TA-090 specific codec module
  • mpegbase_260.prx — MPEG base library
  • me_t2img.img — encrypted ME firmware (392 KB)

All PRX files use Sony’s ~PSP encryption format (magic 0x7E505350). Decryption requires the PSP’s Kirk hardware crypto engine, which we had already used in the USB research for firmware decryption.

Phase 4: RPC Protocol Reverse Engineering

Using the Capstone MIPS disassembly library in Python, we disassembled sceMeCodecWrapper and traced the complete RPC protocol between the main CPU and the Media Engine.

The Command Buffer

All communication flows through a 40-byte command buffer at a fixed uncached memory address: 

ME RPC Command Buffer: 0xBFC00600 (40 bytes)

Offset  Size   Field
──────  ─────  ──────────────────────────────
+0x00   4B     Command ID
+0x04   4B     (reserved/padding)
+0x08   4B     Parameter 1
+0x0C   4B     Parameter 2
+0x10   4B     Parameter 3
+0x14   4B     Parameter 4
+0x18   4B     Parameter 5
+0x1C   4B     Parameter 6
+0x20   4B     Parameter 7
+0x24   4B     Parameter 8
+0x28   4B     Return value (ME writes back here)
+0x2C   4B     (reserved)
The main CPU writes command + params, the ME writes back the return value at +0x28

The address 0xBFC00600 is in the uncached KSEG1 region, ensuring cache coherency between the two processors without explicit flush/invalidate. The main CPU writes the command ID and up to 8 parameters, triggers the ME, and reads the return value from offset +0x28.

The RPC Protocol

Every ME operation follows the same seven-step sequence, extracted from the disassembled wrapper functions: 

ME RPC Dispatch Sequence

1. WaitSema(SceMeRpc)              // Acquire exclusive ME access
2. Write cmd + params to 0xBFC00600  // Fill command buffer
3. DcacheWritebackInvalidate()       // Flush CPU data cache
4. sceSysregMeResetEnable()          // Trigger ME interrupt (!)
5. WaitEventFlag(SceMediaEngineRpc,  // Block until ME signals
                  1, WAIT_AND)       //   completion via event flag
6. Read return value from 0xBFC00628 // ME wrote result here
7. SignalSema(SceMeRpc)              // Release exclusive access
Step 4 is the critical trigger — a SysReg reset pulse acts as the interrupt doorbell

The use of sceSysregMeResetEnable as the interrupt trigger was unexpected. Rather than a dedicated IPC interrupt line, Sony repurposed a SysReg reset signal as a doorbell mechanism. The ME firmware watches for this pulse and reads the command buffer in response.

Command ID Map

From the disassembly, we mapped 22 RPC command IDs to their functions:

CategoryCommandIDDescription
Video Open 0x02 Open video codec instance
Init 0x24 Initialize decoder with SPS/PPS
ScanHeader 0x25 Parse H.264 NAL unit headers
Decode 0x26 Decode one video frame
Release 0xE1 Release video codec resources
Audio Init 0x09 / 0x60 Initialize audio decoder (two variants)

Every video function checks a version constant 0x05100601 before dispatching. This appears to be a firmware compatibility marker — the ME firmware must report a matching version during its boot handshake.

Phase 5: Direct ME Communication — The Breakthrough

With the complete RPC protocol mapped, we needed to test whether the ME would actually respond to direct commands from our homebrew kernel PRX. The key insight: if we loaded our PRX alongside a running UMD movie, the game’s boot process would have already loaded sceMeCodecWrapper and initialized the ME firmware. We could then resolve the ME driver function pointers and call them directly.

Confirming the ME Modules Are Loaded

With Spider-Man 2 UMD video playing, we attempted to load the ME wrapper ourselves: 

sceKernelLoadModule("flash0:/kd/me_wrapper.prx")
  → 0x80020149 (SCE_KERNEL_ERROR_EXCLUSIVE_LOAD)

EXCLUSIVE_LOAD — the module is already resident in kernel memory. The UMD boot process loaded it. This confirmed we could resolve its exported functions without loading our own copy.

Interpreting the Errors

The 0xFFFFFFFF return from sceMeVideo_driver::Init is not a stub error — it is a genuine error code from the ME firmware. The empty stubs in avcodec.prx return 0x806201FE, a completely different value. The ME received our command, attempted to process it, and returned a meaningful failure code.

The error likely indicates that the video codec context was not properly set up. The correct initialization sequence requires calling functions in a specific order: allocate ME memory, open the codec, initialize with video parameters (resolution, profile, level), scan headers (SPS/PPS NAL units), and only then decode frames. We called Init without the preceding steps.

Similarly, RPC command 0x82 returned 0xFFFFFFFD (error -3), which in the ME firmware’s error table corresponds to an invalid state error. The ME is alive, processing commands, and returning structured error codes. It just needs the right initialization sequence.

The Architecture of the Problem

With all five phases complete, we can now explain the full picture of why homebrew H.264 has been broken for two decades:

  1. The user-mode avcodec.prx has empty ME submission stubs. When homebrew calls sceVideocodecOpen, it calls into functions that literally do nothing and return 0x806201FE.
  2. The kernel-mode sceAvcodec_wrapper also has empty stubs. This was a surprise — even kernel-mode code hits the same wall.
  3. UMD boot loads different modules. During the UMD boot sequence, the firmware loads sceMeCodecWrapper (which imports the real ME driver libraries) and replaces or supplements the stub modules. This is why games work.
  4. The ME driver functions are real and work. Calling sceMeVideo_driver functions directly bypasses the empty stubs entirely and communicates with the ME through the RPC protocol.

Phase 6: The Syscall Hook Approach

With direct ME driver calls producing initialization errors, we pivoted to the sceMpeg API — the higher-level interface that Sony’s own games use for H.264 decode. The hypothesis: if we could get sceMpeg to call the real sceAvcodec_wrapper functions (the ones loaded during UMD playback) instead of the empty stubs, the full initialization sequence would happen automatically.

NAL-Based Decode: The ME Accepts Our Data

We first tested whether the sceMpeg API could accept raw H.264 NAL units rather than requiring a full MPEG-PS container. The function sceMpegGetAvcNalAu — previously undocumented in public homebrew SDKs — accepts a NAL unit buffer and produces an SceMpegAu (access unit) suitable for the decoder: 

sceMpegGetAvcNalAu(mpeg, stream_id, nal_buf, au)
  → 0x00000000  // SUCCESS — the ME accepted our H.264 NAL data

This was a significant finding. The sceMpeg layer successfully parsed our NAL units and constructed an access unit for decode. The ME firmware accepted the data. But the next step failed: 

sceMpegAvcDecode(mpeg, au, width, ...)
  → 0x80628002  // AVC_DECODE_FATAL — persistent, every attempt

Error 0x80628002 is distinct from the earlier 0x806201FE. We had progressed past the empty stubs into a real decode attempt, but something in the kernel-side codec path was rejecting it.

Hooking All Five sceMpeg Functions

To redirect sceMpeg calls through the VSH (Visual Shell) library — the version loaded during XMB video playback that connects to the real ME driver — we used sctrlHENPatchSyscall to hook all five critical functions:

FunctionHook TargetResult
sceMpegCreate mpeg_vsh.prx Redirected
sceMpegGetAvcNalAu mpeg_vsh.prx Redirected
sceMpegAvcDecode mpeg_vsh.prx Redirected
sceMpegAvcDecodeDetail2 mpeg_vsh.prx Redirected
sceMpegBaseCscAvc mpeg_vsh.prx Redirected

Same result: 0x80628002. The VSH library itself delegates to sceAvcodec_wrapper in kernel space, which is where the error originates. The hook confirmed that the problem is not in the user-mode mpeg.prx vs mpeg_vsh.prx distinction — both paths converge on the same kernel codec driver.

The Empty Stub at +0x2388: A Red Herring

During Ghidra analysis of sceAvcodec_wrapper, we identified a suspicious empty function at offset +0x2388 in the module’s text segment. It looked like a candidate for the “missing” ME submission function that the stubs should call. After exhaustive cross-reference analysis: zero callers. No function in the entire module references this address. It is dead code, not the missing bridge.

The Kernel Error Table

The actual error originates from sceAvcodec_wrapper’s internal error mapping table at module offset +0x49A0. Ghidra disassembly reveals seven error codes that the kernel driver maps from internal ME return values to user-visible 0x8062xxxx errors:

+0x49B0  0xFFFFFFFE     0x80628002         AVC_DECODE_FATAL (our error)
+0x49B8  0xFFFFFFFD     0x80628003         AVC_DECODE_INVALID_STATE

The ME returns -2 (0xFFFFFFFE) internally, which the kernel maps to 0x80628002 (AVC_DECODE_FATAL)

So the ME firmware receives our decode command, attempts to process it, and returns -2 (fatal error). The kernel driver faithfully translates this to 0x80628002. The question is what state or parameter the ME expects that we are not providing.

PMPlayer: Proof the Hardware Works

To rule out a hardware or firmware defect, we tested PMPlayer Advance on the same PSP (PSP-3001, ARK-4 CFW, firmware 6.61). PMPlayer successfully decodes and plays H.264 video with hardware acceleration. The Media Engine on this exact device is fully functional — the problem is strictly in our initialization or calling convention.

Loading mpeg_vsh.prx: LIBRARY_NOT_YET_LINKED

We attempted to load the VSH MPEG library directly from our kernel PRX using kuKernelLoadModule (a CFW kernel-mode module loader): 

kuKernelLoadModule("flash0:/kd/mpeg_vsh.prx", 0, NULL)
  → module UID (load succeeds)

sceKernelStartModule(uid, 0, NULL, ...)
  → 0x8002012F  // SCE_KERNEL_ERROR_LIBRARY_NOT_YET_LINKED

The module loads into memory but fails to start because it imports libraries that are not yet resident in the kernel. This confirms that mpeg_vsh.prx depends on additional kernel modules (likely sceMeCodecWrapper and its ME driver imports) that are only loaded during UMD boot or VSH video playback.

What We Learned

The investigation revealed a complete, previously undocumented kernel driver architecture and RPC protocol. While the direct RPC approach (Phases 1–5) produced valuable documentation, the actual solution came from a different direction — discovering undocumented parameters in sceMpegCreate by reading PMPlayer’s source code. Sometimes reverse engineering the firmware is less effective than reading existing homebrew that already solved the problem. Key takeaways:

  • Hardware H.264 decode from Rust homebrew is working. The OASIS_OS TV Guide app now streams H.264 video with audio from archive.org on real PSP hardware. The psp::mpeg::AvcDecoder abstraction encapsulates the full decode pipeline in a safe RAII interface — anyone can decode H.264 in ~5 lines of Rust instead of the 200+ lines of unsafe syscalls.
  • AvMpegBase does NOT support the NAL decode path. Tested on real hardware: sceUtilityLoadModule(AvMpegBase) resolves stubs but returns 0x80628002 even with correct mode + DDR top parameters. AvMpegBase only supports the PSMF ringbuffer path (sceMpegGetAvcAu). The NAL path (sceMpegGetAvcNalAu) requires mpeg_vsh370.prx.
  • Codec RPC documentation. The 22 RPC command IDs, buffer layouts, and six-library driver chain are now documented for the PSP homebrew community. The seven-entry kernel error table at +0x49A0 provides the first documented translation between ME internal return codes and user-visible 0x8062xxxx errors.
  • EABI32 is a systemic issue for Rust on PSP. LLVM’s O32 calling convention breaks every PSP syscall with 5+ arguments. The 29 EABI mappers added to rust-psp fix this for all known affected functions, and the pattern is documented for future additions.

Update: EABI32 Breakthrough (2026-03-25)

A marathon debugging session uncovered two critical bugs in rust-psp that were preventing child PRX modules (like mpeg_vsh370.prx) from loading. The symptom: sceKernelStartModule returned 0x800200D3 (SCE_ERROR_KERNEL_ILLEGAL_ADDR) for every call from a Rust EBOOT, while identical C EBOOTs worked perfectly.

Root cause: EABI32 vs O32 ABI mismatch

LLVM’s MIPS target generates O32 calling convention code, where arguments 5–8 go on the stack. The PSP Allegrex CPU uses EABI32, where arguments 5–8 are passed in registers $t0–$t3. For sceKernelStartModule (which takes 5 arguments), the kernel read garbage from $t0 as the pOption pointer, failed address validation, and returned the error.

The fix was straightforward: rust-psp already had EABI32 bridge functions in eabi.rs (i5, i6, i7) written in assembly. They just weren’t applied to all 5+ argument PSP functions. Adding #[psp(NID, i5)] annotations to sceKernelStartModule, sceKernelStopModule, and several other functions resolved the issue.

Second bug: prxgen leaving SHT_REL sections

rust-psp’s prxgen tool left SHT_REL relocation sections (targeting non-ALLOC sections) in the PRX output. The PSP kernel processes all relocation sections it finds, so these leftover entries caused bogus relocations that corrupted module state. The fix: NULL out non-ALLOC SHT_REL section headers during the ELF-to-PRX conversion.

Investigation trail

The debugging effort spanned kernel module dumps (modulemgr at 0x8805A400, loadcore at 0x88017000), MIPS disassembly of the PSP firmware’s _PrologueModule function, K1 register patching experiments, ARK-4 CFW source analysis, C/Rust hybrid test EBOOTs, syscall number comparisons, and progressive binary morphing. The full details are in docs/psp-child-module-investigation.md.

With child module loading now working, the path to hardware H.264 decode via mpeg_vsh370.prx was unblocked — leading directly to the sceMpeg integration work described in the next section.

Update: sceMpeg Integration (2026-03-25)

With the EABI fix confirmed, the focus shifted to actually calling sceMpeg functions from the Rust EBOOT. This turned out to be a deep exploration of the PSP kernel’s module linking behavior.

Import stub resolution: what works, what doesn’t

The PSP kernel resolves import stubs (weak 0x0009 flags) at module load time. We tested every combination:

ApproachStubs resolve?AvcDecode works?
sceMpeg stubs + AvMpegBase (sceUtilityLoadModule) Yes — utility loader triggers re-linking No — 0x80628002 (AvMpegBase does not support NAL decode path)
sceMpegVsh_library stubs + mpeg_vsh370 (sceKernelStartModule) No — kernel does NOT re-link after StartModule N/A
Both AvMpegBase + mpeg_vsh370 N/A Conflict: 0x8002013b (exclusive load)
sceMpeg stubs + mpeg_vsh370 only (no AvMpegBase) Yes! mpeg_vsh370 registers “sceMpeg” for self-imports 0x80628002 — but Init/Create/GetAvcNalAu all succeed

The surprise: mpeg_vsh370 registers “sceMpeg”

mpeg_vsh370.prx imports 59 functions from the sceMpeg library (self-referencing). When the kernel links these at StartModule time, it effectively registers sceMpeg as an available library — which triggers re-linking of the EBOOT’s sceMpeg weak import stubs. This means we can call sceMpeg functions through mpeg_vsh370 without any kernel PRX or bridge module.

Key discoveries along the way

  • Module loading during preinit freezes the GU — sceKernelLoadModule for mpeg_vsh370 must be called from the video thread, not the main thread. Loading during init causes a dashboard freeze (likely EDRAM partition conflict with framebuffers).
  • The kernel PRX corrupts networking — sctrlHENPatchSyscall hooks on sceMpeg functions corrupt adjacent syscall table entries used by sceHttp/sceNet, causing WiFi dialog errors (80082731, 80020190) and HTTP parse hangs. This cost hours of debugging.
  • ELF headers stripped after module load — the kernel removes ELF/program headers from loaded PRX modules, making it impossible to walk the export table from user mode.
  • ARK-4 CFW caches kernel plugins — renaming the PRX file doesn’t force a reload; the CFW loads from a cached copy.

oasis-me-boot.prx: Rust replacement for cooleyesBridge

We rewrote cooleyesBridge.prx (GPL, by cooleyes) as a clean Rust kernel PRX: oasis-me-boot.prx. It uses sctrlHENFindFunction to resolve sceMeBootStart660 (NID 0x5DFF5C50 in sceMeCore_driver), clears $k1 for kernel address validation, and calls it with mebooterType=0. No GPL dependency, no syscall patching, no networking corruption.

The 0x80628002 mystery: ME decodes for PMPlayer but not for us

Despite getting every sceMpeg function to succeed — Init, Create, RingbufferConstruct, RegistStream, MallocAvcEsBuf, InitAu, AvcDecodeMode(Psm8888), GetAvcNalAu — sceMpegAvcDecode consistently returns 0x80628002 (AVC_DECODE_FATAL). We confirmed:

  • ME boot is not the issue — sceMeBootStart660(0) returns 0x80000102 (already booted by the AAC subsystem). Same error with or without boot.
  • PMPlayer works on this exact PSP with the same mpeg_vsh370.prx and cooleyesBridge.prx. H.264 decode is hardware-capable.
  • The ME IS processing — one frame occasionally returns 0x80628001 (less fatal error), confirming the ME receives and attempts to decode our data.
  • All configuration variants tested: mode 0, mode 5, with/without AvcDecodeMode, with/without ME boot, proper ringbuffer construction — all return 0x80628002.

The remaining hypothesis: our Mp4AvcNalStruct data formatting or NAL prefix handling differs from PMPlayer’s. The H.264 data may have AVCC length prefixes where the ME expects Annex B start codes, or the struct layout may have additional fields we’re not populating.

Root cause found: PMPlayer source code comparison

Finding PMPlayer’s actual source code (pmplayer-advance by cooleyes, exported from Google Code to GitHub: DavisDev/pmplayer-advance, key file: /ppa/mod/mp4avcdecoder.c) revealed three critical differences in our sceMpegCreate call:

ParameterOur CodePMPlayerImpact
sceMpegQueryMemSize mode 0 4 (≤480p) / 5 (>480p) Different buffer size, NAL decode path not enabled
sceMpegCreate unk1 0 mpeg_mode (4/5) ME doesn’t know which decode mode to use
sceMpegCreate unk2 0 DDR top pointer (4MB-aligned 2MB buffer) ME has no workspace for decoded frames — root cause of 0x80628002
AU buffer for sceMpegInitAu sceMpegMallocAvcEsBuf ddrtop + 0x10000 AU not in DDR top region where ME expects it
AU struct init zeroed memset(0xFF) Sentinel values required for proper state tracking

The “unknown” parameters in sceMpegCreate were never documented in PSPSDK or any public reference — they were only visible in PMPlayer’s source. Without the DDR top pointer, the ME’s codec firmware had no output buffer to write decoded YCbCr frames, causing every sceMpegAvcDecode call to return 0x80628002 (AVC_DECODE_FATAL).

H.264 decode: working!

After applying all three fixes, the full decode pipeline works on real PSP hardware. Confirmed with a 656×480 H.264 stream from archive.org (Bits and Bytes, 1983). The working init sequence: 

sceMpegInit() = 0x0
sceMpegQueryMemSize(5) = 49535        // mode 5 for >480p
DDR top: 2MB @ 0x9000000 (4MB-aligned)
sceMpegRingbufferConstruct(8 packets) = 0x0
sceMpegCreate(mpeg, data, 49535, &rb, 512, 5, 0x9000000) = 0x0
sceMpegRegistStream(mpeg, 0, 0) = OK
sceMpegInitAu(mpeg, 0x9010000, &au) = 0x0   // ddrtop + 0x10000, AU filled with 0xFF first
sceMpegAvcDecodeMode(mpeg, {-1, Psm8888}) = 0x0

The per-frame decode sequence feeds AVCC-format NAL data (length-prefixed, directly from MP4 container) via sceMpegGetAvcNalAu, then decodes via sceMpegAvcDecode. The ME outputs YCbCr which is converted to ABGR via sceMpegBaseCscAvc (hardware color space converter). One additional fix: the CSC outputs alpha=0x00, so a post-conversion alpha fixup sets every pixel’s alpha to 0xFF for correct compositing.
